SECURITY AND DATA HANDLING

Know what is stored.
Control the record.

A concise description of the current development build's processing, access and persistence model. This is not a security certification.

01 / DOCUMENT PROCESSING

Source files stay in request memory.

The application reads uploaded documents for extraction and comparison. It does not intentionally write the original uploaded files to persistent storage. Each file is limited to 15 MB. Office documents are checked for archive entry count, expanded size and suspicious compression ratios. PDFs are limited to 500 pages.

02 / PERSISTENCE

Extracted evidence is sensitive too.

When access-token protection is configured, the application stores the extracted report, parameter values, filenames, source excerpts and reviewer events in SQLite. This content may still be confidential engineering information. Protect the database, backups and host accordingly.

Without a configured token, comparisons and exports work but investigations and review events are not persisted.

03 / ACCESS

Single shared bearer token.

When DATASHEETDELTA_ACCESS_TOKEN is configured, the token is required for comparison, export and review endpoints. The browser keeps the token in session storage for the current tab and sends it in the Authorization header.

This is a trusted single-operator access model. Reviewer names are self-entered. There is no per-person identity, role-based access control, SSO or multi-tenant isolation.

04 / REVIEW HISTORY

Append-only within the application.

Review events are stored with a SHA-256 hash chain. Application-level update and delete triggers prevent ordinary event mutation. On retrieval, the application checks the report hash and event chain.

This detects accidental or ordinary database changes. It cannot prevent a database administrator from rewriting the database and recomputing hashes. Deleting an investigation removes its report and all associated review events.

05 / DEPLOYMENT RESPONSIBILITY

Secure the environment.

  • Use TLS and restrict network access.
  • Use a long random token and rotate it when needed.
  • Keep SQLite storage and backups access-controlled.
  • Review reverse-proxy logs; do not log authorization headers or upload bodies.
  • Back up the database and test restoration.
  • Do not expose the development build to untrusted users or process restricted documents without approval.

The current build does not provide parser sandboxing, rate limiting, malware scanning, encrypted database storage or enterprise identity. It is not approved for regulated or confidential document processing.
